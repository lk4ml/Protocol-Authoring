Key Gaps

1. Architecture Overview

TrialForge
  • 22 node types — lean, protocol-centric schema
  • 32 relationships — all entities owned by Protocol hub
  • Flat versioning — single version field on Protocol
  • No CT layer — CDISC codes stored as string properties
  • Dual-write — SQLite primary + Neo4j graph
  • Single-study focus — each Protocol is independent
  • JSON blob migration — study_design_data exploded into graph nodes
OpenStudyBuilder
  • 94+ node types — enterprise schema with full CDISC CT
  • 200+ relationships — cross-study library + versioning edges
  • Root-Value versioning — every entity has Root node + versioned Value nodes with LATEST_FINAL/LATEST_DRAFT/HAS_VERSION pointers
  • Full CT layer — all CDISC codelists loaded as graph nodes
  • Neo4j-only — no SQL database at all
  • Library-first — shared Activity/Compound/CT concepts across studies
  • Native graph — built on Neo4j from day one
Key Architectural Difference
TrialForge stores everything under a single Protocol hub node. OpenStudyBuilder separates library-level concepts (Activity definitions, Compounds, CT terms) from study-level instances, enabling cross-study reuse. OSB's Root-Value pattern means every node has two layers: a stable Root (identity) and versioned Values (state snapshots).

  • Single node per entity — no history
  • Updates replace properties in-place
  • version is a string field on Protocol only
  • No audit trail — previous state is lost
  • Pro: Simple queries, fast writes
  • Con: No change tracking or rollback

    classDef root fill:#da6d25,stroke:#f0883e,color:#fff
    classDef final fill:#238636,stroke:#3fb950,color:#fff
    classDef draft fill:#8b5cf6,stroke:#a78bfa,color:#fff
  • Root node: stable identity (never changes)
  • Value nodes: versioned state snapshots
  • LATEST_DRAFT → current working copy
  • LATEST_FINAL → last approved version
  • LATEST_RETIRED → deprecated version
  • Pro: Full history, rollback, concurrent edits
  • Con: 2x nodes, complex queries, garbage collection

6. Gap Analysis & Roadmap

# Gap Priority What OSB Does TrialForge Recommendation
1 Versioning High Root-Value pattern with LATEST_DRAFT / LATEST_FINAL / HAS_VERSION pointer relationships on every entity Start with Protocol-level versioning (snapshot entire graph). Add entity-level Root-Value later if needed for concurrent editing.
2 CT Integration High Full CDISC CT loaded as graph nodes (CTCodelist, CTTerm, CTTermContext). Every coded field links to a CT term node Load CDISC CT as graph nodes during startup. Replace string codes (typeCode, levelCode) with relationships to CTTerm nodes. Start with CT packages used in your active TAs.
3 Activity Library Medium 4-level hierarchy (Group → SubGroup → Concept → Instance) as reusable library, separate from study-level Extract current activities into library nodes. Study activities become references to library concepts. Enables cross-study activity reuse.
4 Audit Trail Medium StudyAction nodes (Create/Edit/Delete) with BEFORE/AFTER edges. Full change history with user attribution Add StudyAction nodes on each write. Store timestamp + user + action type. BEFORE/AFTER edges to affected nodes.
5 ODM / CRF Model Medium OdmForm, OdmItemGroup, OdmItem, OdmCondition, OdmMethod nodes. Full CRF structure as graph Phase 2+ feature. Map activities → ODM forms → item groups → items. Enables CRF generation from SOA.
6 SDTM Mapping Low DatasetRoot, DatasetScenario, DatasetVariable. Activities linked to SDTM domains/variables Leverage existing sdtmDomain property on Activity. Add Dataset nodes + relationships later for full mapping.
Strategic Takeaway
TrialForge's 22-node schema covers the core protocol authoring workflow effectively. The biggest architectural gaps versus OSB are versioning and CT integration. Versioning enables regulatory-grade change tracking; CT integration enables proper CDISC compliance. Both are achievable incrementally without redesigning the existing schema — they add new node types and relationship layers on top of what exists.
